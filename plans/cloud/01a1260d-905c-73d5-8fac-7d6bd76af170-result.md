## Decisions

- Starter `blank` uses **no theme**: it is the scaffold `nera new` makes today; any theme is one `theme:` line away.
- Starter `portfolio` uses **`theme-business`** (`pages/list.pug` card grid of child pages + `pages/gallery.pug` image grid), because a portfolio also needs the hero, the contact page and the legal footer; the blog's single reading column is wrong for image grids.
- `nera.generator: ">=4.15.0"`, no upper bound: the themes rely on `app.theme.config` (4.6.0), frontmatter `date` → `createdAt` (4.7.0) and per-page `yaml` frontmatter (4.15.0); an upper bound would fail every site's build when core 5 ships.
- Peer ranges use the **verified release as the floor** (`^1.1.1`, not `^1.0.0`): the classes were checked at that version, and a minor may have added one; every peer is optional.
- The themes use the conventional paths `layouts/layout.pug` and `pages/default.pug` (as theme-example does), so the base template's `pages/index.md` renders with them; `nera new --theme` already leaves out the scaffold's copies.
- Plugin output reaches a themed page only through **seam partials** the site overrides (e.g. `partials/nav-main.pug`, `partials/contact-form.pug`); the theme never reads plugin data itself, so a plugin's data shape can never break a theme.
- One shared **token set** (`tokens.color|font|size.*` → `--theme-<group>-<name>`), emitted as one inline `<style>:root{…}</style>` with a value filter (`<>{};` dropped); `theme.css` repeats every default as a `var()` fallback.
- Two theme keys besides tokens: `extra_css` (root-absolute paths only, so no third-party stylesheet) and `footer_links` (label = `t()` key, href per language) — the latter is where the legal links live.
- Business facts (address, phone, opening hours) live in the site's `config/app.yaml` under `business:` — site facts, not presentation, so they survive a theme switch.
- Every page type renders exactly one `<h1>` from `meta.title` (or the hero title); page bodies start at `##`. Exception: the blog tag page, whose seam owns the `<h1>` because plugin-tags' `tag-overview` renders its own.
- Language switch from core data only: match by `meta.slug` (the identifier plugin-canonical-links uses by default), else the language's home page; labels from each language's `language_name` translation.
- No theme JavaScript, no font files and no dark mode in 1.0: system font stacks; self-hosted webfonts are the site's; dark mode would be a later minor (`color_dark` tokens).
- No theme-shipped translations: `t()` with English keys, the starters carry `translations.de` (core cannot merge theme translations today — T3).
- Blog post selection by `meta.layout` in `blog.post_layouts` (default `['pages/post.pug']`), newest first by `createdAt`; list pagination is out of reach for a theme (T1), so home = newest `blog.home_posts`, archive = all.
- Theme semver: raising the `nera.generator` floor or dropping a plugin major is **major**; changing a token's default value is **minor**.

## Review hints

- **S2.5 token emission.** The inline `<style>` with a value filter is my design; check you are happy with an inline style (T5, strict CSP) versus asking for a companion plugin.
- **S2.8 language switch** relies on `meta.slug` matching across translations and on `app.translations` keys listing the site's languages. A site with a `translations` entry for a language that has no pages simply gets no link for it (rule 3) — check that is the behaviour you want.
- **S3.1 `app.business`** is a new `config/app.yaml` key read by a theme. Core passes every `app.yaml` key through, so it works today, but it is a convention the CLI/validate do not know about.
- **S6 item 4** (labelling the published page-pagination `<nav>`) and item 5 (social links `target`) put work on the starters that would be better fixed in the plugins.
- **S7 "Without plugins"** assumes every seam's default renders nothing broken; the blog tag-page seam's default (h1 + body) only matters when plugin-tags is absent, in which case no tag pages exist anyway.
- **`a11y-h1`** is a real rule in validate 1.4.2 (default `warning`) though the brief's list omits it; the one-`<h1>` rule in S2.2 follows from it.
- **Not built, only specified.** Nothing here was rendered with Pug; the views are described, not implemented. The Pug snippet in S2.5 is marked "normative behaviour, not normative code" and was not executed.
- `@nera-static/nera` moved to **1.10.1** on npm during the session (packed and read at 1.10.0); the spec's `^1.10.0` devDependency covers both.
