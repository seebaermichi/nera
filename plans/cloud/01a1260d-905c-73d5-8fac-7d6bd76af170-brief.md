```text
Modelled on Statamic's starter kits (decision D5): a theme is presentation
only; a **starter kit** is a whole ready-to-edit site — sample pages, config,
plugins wired up, and a theme dependency.

- **Package:** `@nera-static/starter-<name>` on npm (own repos
  `nera-starter-<name>`, flat siblings like the plugins), with a `nera.starter`
  field in `package.json` naming its human label and description. Third parties
  publish their own; `--starter` accepts a bare name (`blog` →
  `@nera-static/starter-blog`), a package name, a GitHub URL, or a local path —
  the same forms `--theme` accepts today (`validateThemeSpec` in `scaffold.js`).
- **Contents:** `pages/`, `config/`, optional site-level `theme/` overrides,
  `assets/`, a `package.json` fragment (`dependencies`: the theme and plugins),
  and an optional `README` shown after scaffolding.
- **Behaviour:** `nera new` copies the starter over the base template, merges the
  dependencies, applies `--name`/`--lang` to `config/app.yaml`, installs. After
  that the starter is gone — the site owns the files (no update path, by
  design, as with Statamic). The theme it depends on still updates via npm.
- **First set:** `business` (home, about, services, opening hours, contact form,
  imprint, privacy), `blog` (tags, pagination, feed, sitemap), `portfolio`
  (images). Each needs a real theme — at least two new themes beyond
  `theme-example`; theme specs live in `generator/ROADMAP-themes.md`.
```

### Rules from the workspace (`CLAUDE.md`, not visible to you)

- **A theme's relationship to plugins is CSS only** (§4 of the spec): it never
  ships `views/vendor/`, never a plugin's `.pug`. Plugin templates are copied into
  the **site** with each plugin's `npm run publish-template`
  (`views/vendor/<plugin-name>/`) and included by hand; the site (= the starter)
  does that, not the theme. The theme's job is to style the plugins' BEM classes
  and to offer include points (blocks/partials) where a site puts them.
- **Template markup and BEM class names are a semver contract**: changing them is
  a **major** for a plugin, and for a published theme too (issue conventions).
  So the spec must name the theme's own public classes / blocks / partials as its
  contract.
- Plugin config is read from the site's `config/<name>.yaml` only (no merge);
  `config/theme.yaml` deep-merges (§1c, §3). A theme never relies on plugin config
  it cannot see.
- Pages without `layout` in frontmatter are never rendered; `public/` is deleted
  on every build; a plugin writes files via the `getAssets` hook (core ≥ 4.13.0).
- `t(key)` resolves `app.translations[meta.lang || app.lang][key]`, falling back
  to the key. Starters are multilingual-capable (en/de at least): every UI string a
  theme renders goes through `t()` with English keys, and the spec lists them.
- Every published package's README carries the Test and npm badges; new repos are
  secured like the fleet (ruleset, secret scanning, Dependabot, private
  vulnerability reporting, FUNDING.yml). One line in the spec's release part is
  enough.
- Interface and docs language: English. Style is enforced by eslint where JS
  exists: ESM, 4-space indent, no semicolons, single quotes.
